# 1. 项目目标

AI Dev OS 是一套基于 AI Agent、MCP（Model Context Protocol）与自动化工具链构建的**个人智能开发操作系统**，目标不是简单安装几个 AI 工具，而是建立完整软件开发工作流：

- AI 理解需求
- AI 分析项目
- AI 辅助编码
- AI 管理版本
- AI 管理开发环境
- AI 执行自动化测试
- AI 输出开发报告

核心思想：

    Agent 负责思考和决策
    MCP 负责能力调用
    用户负责最终控制

v1.0.0 的落地形态是一个可运行的任务编排核心（`services/orchestrator`），围绕"先理解、先计划、等待确认、可追踪执行、失败停止"五个原则，实现从用户需求到多 Agent 执行、审计追踪的完整闭环。

# 2. 总体架构

## 2.1 分层视图

    用户
     ↓
    API / 前端（Vue 3 + TypeScript）
     ↓
    Orchestrator（Spring Boot 4 / Java 21）
     ├── Planning（Hermes Planner → PlanDraft → Plan Validator）
     ├── Plan Approval（人工批准，版本冻结）
     ├── PlanScheduler（PlanRun 串行 DAG 调度）
     ├── Job / JobWorker（异步执行，Lease 控制）
     ├── ExecutionEngine（Agent 解析 → Executor 调用）
     └── Audit / Timeline（事件记录与查询）
     ↓
    Agent / Executor 层（Hermes / Codex / OpenClaw / Tool / Mock）
     ↓
    MCP 能力层（Filesystem MCP、Tool Router、审批策略）
     ↓
    外部资源（Codex CLI、OpenClaw Gateway/浏览器、PostgreSQL、本地文件系统）

## 2.2 状态真相

- 默认 `in-memory` 模式：Task、Agent、Job、ExecutionRecord、Schedule、PlanRun 等保存在进程内存。
- 生产 `postgresql` 模式：业务状态与审计事件持久化到 PostgreSQL，多实例共享同一数据库，靠数据库原子性保证并发安全。

## 2.3 技术栈

- 后端：Java 21、Spring Boot 4.0.0、Maven
- 前端：Vue 3、TypeScript、Vite（开发端口 `15174`，`/api` 代理到后端 `18080`）
- 数据库：PostgreSQL（JSONB + 版本化迁移）
- 外部依赖：Codex CLI（本地 `codex exec`）、OpenClaw Gateway（`ws://127.0.0.1:18789`）、MCP stdio server（filesystem）

# 3. Agent 体系

## 3.1 角色定义（`configs/agents/*.yaml`）

| Agent | 文件 | 职责 | 关键权限边界 |
| --- | --- | --- | --- |
| Hermes | `hermes.yaml` | 需求分析、任务拆解、计划生成、流程协调 | 只读项目与文档；禁止修改代码、提交、改系统 |
| Codex | `codex.yaml` | 代码实现、重构、Bug 修复 | 允许写代码/跑测试；`git add/commit`、docker 需确认；禁止 `git push`、删项目、改系统 |
| OpenClaw | `openclaw.yaml` | 浏览器自动化、GUI 操作、环境操作 | 允许打开页面/点击/输入/截图/验证；登录、提交表单需确认；禁止改业务需求与源码 |
| Tester | `tester.yaml` | 测试执行、验证、报告生成 | 允许跑测试/收日志/出报告；禁止改业务代码、改需求、`git push` |

## 3.2 运行时 Agent（`src/main/resources/agents.yaml`）

| name | executor | capabilities | 说明 |
| --- | --- | --- | --- |
| `planner` | `mock` | `analysis` | 运行时解析为 Mock，不调用外部 Planner |
| `executor` | `mock` | `coding`, `git` | Mock 执行 |
| `coder` | `codex` | `coding`, `git` | 调用本地 `codex exec` CLI |
| `tester` | `openclaw` | `testing`, `browser` | OpenClaw agentId `main` |
| `browser-agent` | `openclaw` | `browser` | OpenClaw agentId `main` |
| `mcp-reader` | `tool` | `tool`, `read-only` | 通过 ToolRouter 调用声明的只读工具 |

## 3.3 三个核心 Agent 的实现

### Hermes（Planner）

- `HermesPlanner` 实现 `Planner` SPI，由 `PlannerService` 调用，生成不可变 `PlanDraft`。
- 默认生成固定单 Step Plan；当结构化输入 `multiAgent=true` 时生成多 Agent 模板计划：
  `browser-inspect → mcp-read → code-fix → browser-verify`（含依赖边与 Artifact 引用）。
- `replan()` 基于失败分类生成下一版本 Plan（version+1），需重新审批。
- 运行时 `planner` Agent 仍映射 `mock` executor，Hermes 作为"计划生成器"而非"执行 Agent"。

### Codex（Coder）

- `CodexExecutor` 通过 `CommandExecutor` 包装本地 `codex exec` CLI，配置 `workspace`、`model`、`sandbox=workspace-write`、审批策略与超时。
- `GitInspector` 在执行前后采集 status、branch、HEAD、diff、cached diff 与 untracked 文件，产出 Git Artifact。
- `CodingApprovalService` 对 workspace-write 编码任务做内存审批（requested → approved → consumed）。
- 设计原则：不自动 commit、不自动 push，HEAD 保持不变。

### OpenClaw（Tester / Browser Agent）

- `OpenClawExecutor` 经 `OpenClawTaskService` 连接 OpenClaw Gateway。
- `OpenClawWebSocketClient` 实现 Protocol v4：connect 握手（token、设备 identity、签名、operator scopes）、request 关联、超时与错误转换。
- 执行闭环：`agent → agent.wait → chat.history`；Browser 参数分支支持 navigate/click/input/screenshot 等 action 并映射截图 Artifact。

### Tool（MCP Reader）

- `ToolExecutor` 读取 `parameters.tool`（provider/server、name、arguments、timeout），经 `ToolRouter` 调用注册的 MCP 工具，把 `ToolResult` 映射为 `ExecutionResult` 与 Artifact。

# 5. 核心模型

## 5.1 模型链

    PlanRun
      ↓ 1..n
    StepRun
      ↓ 1..n
    StepAttempt
      ↓ 1..1（提交确定性 Job）
    ExecutionJob
      ↓ 1..n
    ExecutionAttempt
      ↓ 1..1
    Executor（AgentExecutor）
      ↓
    ExecutionResult → ExecutionRecord / Artifacts

## 5.2 PlanRun / StepRun / StepAttempt（`plan/run`）

- `PlanRun`：`id`、`approvalId`、`plan`（含 `planId`/`planVersion`）、`steps`、`status`、`version`（CAS）、coordinator lease 字段（`coordinatorOwner`/`coordinatorToken`/`coordinatorExpiresAt`）。
- `PlanRunStatus`：`DRAFT → RUNNING → SUCCESS / FAILED / WAITING_APPROVAL / REPLAN_REQUIRED`。
- `StepRun`：`stepId`、`attempts[]`、`status`；`StepRunStatus`：`PENDING → RUNNING → SUCCESS / FAILED / WAITING_APPROVAL / SKIPPED`。
- `StepAttempt`：`number`（从 1 递增）、`jobId`、`executionRecordId`、`error`。
- 每个 Step 的 Job ID 采用确定性格式（`job-{attemptId}`），配合 `createIfAbsent` 实现并发/重启幂等。

## 5.3 ExecutionJob（`job`）

- 内容：`taskSnapshot`（Task 快照）、`status`、`attemptNo`/`maxAttempts`、`availableAt`/`priority`、lease 字段（`leaseOwner`/`leaseToken`/`leaseExpiresAt`/`heartbeatAt`）、`version`、`recoveryCount`、`lastFailureCode`、`recoveryPolicy`（默认 `MANUAL`）、`approvalId`、`executionRecordId`。
- `JobStatus`：`QUEUED / RUNNING / WAITING_APPROVAL / SUCCESS / FAILED / RETRY_WAIT / CANCELLED / RECOVERY_REQUIRED`。

## 5.4 ExecutionAttempt（`execution`）

- 内容：`jobId`、`attemptNo`、`executionId`、lease 字段、`failureCode`、`recoveryCount`、起止时间。
- `ExecutionAttemptStatus`：`STARTING → RUNNING → SUCCEEDED / FAILED / ABANDONED / RECOVERY_REQUIRED`。

## 5.5 Executor（`executor`）

- `AgentExecutor` SPI，注册表 `ExecutorRegistry`（type → 实现）：
  - `mock`：`MockAgentExecutor`
  - `codex`：`CodexExecutor`（CommandExecutor + GitInspector）
  - `openclaw`：`OpenClawExecutor`（OpenClawTaskService）
  - `tool`：`ToolExecutor`（ToolRouter）
- 执行产出 `ExecutionResult`（success/message/output/artifacts/approvalRequired/approvalId/metadata），`ExecutionRecordManager` 捕获为 `ExecutionRecord`，内含 `ExecutionReport` 与 `ExecutionArtifact`（截图、git diff、文件内容等，受限截断）。

## 5.6 状态推进示例（编码 Step）

    PENDING → RUNNING（提交 Job）
      → WAITING_APPROVAL（审批）
      → RUNNING（批准后 resume）
      → SUCCESS / FAILED（按结果与 Artifact 门槛判定）

# 6. Reliability 设计

## 6.1 PostgreSQL Persistence

- 双模式：`aidevos.persistence.type=in-memory|postgresql`；生产必须 `postgresql`。
- 版本化迁移 `src/main/resources/db/migration/V1..V7`，由 `PostgresDocumentStore` 启动时按版本顺序应用并记录 `schema_migrations`，幂等可重复启动。
  - `V1`：`repository_documents`（通用 JSONB 文档表，PlanRun/Agent/Approval 等）、`uq_plan_run_approval` 唯一约束。
  - `V2`：`audit_events`（事件表 + 各聚合维度索引）。
  - `V3`：Plan 版本冻结（数据库级 PlanVersion freeze）。
  - `V4`：`audit_outbox`（事务 outbox 表）。
  - `V5`：`jobs`/`execution_attempts` 结构化控制列（lease、attempt、version、recovery）。
  - `V6`：`repository_documents.version`（PlanRun CAS 列）。
  - `V7`：outbox relay 控制列（`topic`/`next_attempt_at`/`dead_lettered_at`）与 `idx_audit_outbox_claim`。
- 就绪门禁：`ReadinessGate` 在启动完成且 V1～V7 全部应用前，`/api/health/readiness` 返回 `503 NOT_READY`。

## 6.2 Lease / Fencing

- `claimNext`：单条 SQL 原子 claim（`FOR UPDATE SKIP LOCKED` + 状态过滤 + `lease_token=COALESCE(lease_token,0)+1`），同一 Job 只会被一个 worker 抢到。
- Heartbeat：独立调度线程按 lease/3 周期 `renewLease(jobId, owner, token, newExpiry)`；lease 被接管后续期失败即停止心跳。
- Fencing：所有 lease 绑定写操作（`renewLease`/`releaseLease`/`complete`）必须携带 `owner + token`；`WHERE lease_owner=? AND lease_token=?` 影响行数为 0 即表示已被接管，写入被拒绝，防止旧实例覆盖新实例。
- `LeaseReaper`：周期扫描过期 lease（`findStale`），将 `RUNNING` 且 lease 过期的 Job 原子标记为 `RECOVERY_REQUIRED`（`LEASE_EXPIRED`、`recovery_count+1`、清除 lease）。

## 6.3 CAS（Compare-And-Swap）

- PlanRun 推进：`claimCoordinator` 拿到 coordinator lease（owner + token），每次 reconcile 记录 `claimedVersion`，结束前 `saveIfUnchanged(run, claimedVersion)`，版本不一致即放弃，防止两个 scheduler 实例重复推进同一 run。
- 幂等提交：Step Job 使用确定性 ID + `createIfAbsent`（`ON CONFLICT DO NOTHING`）；PlanRun 创建使用 `createIfAbsent(approvalId, run)` + 审批消费唯一性。
- Job 表 `version` 列：每次 lease 写操作 `version=version+1`，为 CAS 与观测提供依据。

## 6.4 Recovery

- 保守原则：过期/丢失的 Job 一律进入 `RECOVERY_REQUIRED`，不会自动重跑可能产生副作用的任务，等待人工裁决。
- `LeaseReaper`（Job 维度）：`LEASE_EXPIRED`。
- `ExecutionAttemptRecovery`（Attempt 维度）：`findAbandoned` → `markAbandoned` → `markRecoveryRequired(STALE_EXECUTION)` → 清除 lease。
- 人工恢复路径：确认外部副作用未发生或可安全重放后，将 `RECOVERY_REQUIRED` 恢复为 `QUEUED`。

## 6.5 Transactional Outbox

- 目标：保证"业务状态提交"与"审计事件入队"同事务，避免事件丢失。
- `PostgresOutboxTransactions` + `JdbcConnectionContext`：回调内的 repository 写操作与 `enqueue` 共享同一 JDBC 事务，一起 commit/rollback。
- `OutboxRelay`：后台每 tick `claimPending`（`FOR UPDATE SKIP LOCKED` 批量）→ 每条消息一个事务发布 → 成功 `markPublished`，失败按指数退避（`backoff-base` → `backoff-max`）→ 达到 `max-attempts` 进入死信（`dead_lettered_at`）。
- 语义：at-least-once 投递 + `idempotencyKey` 去重；发布失败不回滚已提交的业务事务。
- 进程崩溃后，新实例 relay 从 pending 行继续恢复。

# 7. Audit 与 Timeline

## 7.1 事件模型（`audit`）

- `EventRecord`：`id`、`type`、`occurredAt`、`sequence`、`aggregateType/Id`、`fromStatus/toStatus`、关联键（`taskId`、`planId/planVersion`、`planRunId`、`stepRunId`、`attemptId`、`jobId`、`executionId`、`executionRecordId`、`invocationId`、`approvalId`）、`actorType/Id`、`summary`、`metadata`、`idempotencyKey`、`schemaVersion`。
- `EventType` 覆盖：Job（submitted/started/succeeded/failed/approval/recovery）、Execution（started/completed/failed/waiting_approval）、Step/PlanRun 迁移、Agent 选择与执行、Tool/MCP 调用、三类审批（Coding/Plan/Tool）、Artifact、Replan 等。
- `AuditService` 统一记录；`PostgresAuditRepository` 将过滤、分页、count 下推到 SQL；`audit_events` 建立各聚合维度索引。

## 7.2 Timeline（`audit/timeline`）

- `TimelineService` 提供三种 scope：`planRun(id)`、`execution(id)`、`job(id)`。
- `ExecutionTimeline`：`scopeType`、`scopeId`、`offset/limit`、`count`、`totalCount`、`hasMore`、`events`。
- API：`GET /api/audit/events`（聚合查询），`GET /api/timelines/plan-runs/{id}`、`/api/timelines/executions/{id}`、`/api/timelines/jobs/{id}`。
- 前端提供 Audit Console：查询、过滤、分页与时间线展示。

## 7.3 典型事件链

    PLAN_RUN_CREATED → STEP_SUBMITTED → JOB_SUBMITTED → JOB_STARTED
      → AGENT_SELECTED → EXECUTION_STARTED → TOOL_INVOCATION_* / MCP_CALL_*
      → EXECUTION_COMPLETED → EXECUTION_RECORD_SAVED → JOB_SUCCEEDED
      → STEP_SUCCEEDED → PLAN_RUN_TRANSITION

# 8. MCP 能力层

## 8.1 目标与原则

- Agent 负责决策，MCP 负责执行；能力模块化、权限可控制、工具可扩展。
- 默认只读，修改需授权，危险操作必须人工确认。

## 8.2 Tool 核心（`tool`）

- 模型：`ToolDefinition`、`ToolInvocation`（provider/name/arguments/timeout）、`ToolResult`、`ToolContent`、`ToolArtifactMapper`。
- `ToolRegistry` 注册 `ToolProvider`；`ToolRouter.invoke` 完整链路：

      ToolInvocation → 审计(TOOL_INVOCATION_CREATED)
        → 查找 Tool/Provider → ToolPolicy 评估
        → DENY → 审计并返回失败
        → REQUIRE_APPROVAL → ToolApprovalService（approvalId，等待/授权）
        → 虚拟线程执行 Provider（超时/中断保护）
        → 审计 TOOL_COMPLETED / TOOL_FAILED → ToolResult

- `ToolPolicy`（`AllowRegisteredToolPolicy`）动作：`ALLOW` / `DENY` / `REQUIRE_APPROVAL`。

## 8.3 MCP Client（`tool/mcp`）

- `McpSession`（`McpStdioSession`）：stdio 子进程会话，`initialize` / `tools/list` / `tools/call`，JSON-RPC。
- `McpClient` 包装会话与超时；`McpToolProvider` 暴露为 ToolProvider。
- 配置 `tools.mcp.enabled`（默认 `false`）、`providerId`（默认 `filesystem`）、`command`、`requestTimeout`（默认 30s）。
- `.mcp/config.json`：本仓库注册 filesystem MCP server，命令 `mcp-server-filesystem`，根目录为工作区。

## 8.4 接入执行链

- `mcp-reader` Agent（executor `tool`，capabilities `tool/read-only`）让 PlanStep 通过 `parameters.tool` 直接声明调用只读工具。
- 权限分层：`configs/execution/development.yaml` 定义 `auto_execute`（只读、git status/diff、test/build、docker ps/logs）、`require_confirm`（写文件、git add/commit、docker build/run）、`always_confirm`（删除、git reset/push、系统修改）。
- 结果经 `DefaultToolArtifactMapper` 映射为 `ExecutionArtifact`，随 ExecutionRecord 保存与审计。

# 10. v1.0 限制与未来路线

## 10.1 已知限制

- **默认内存模式**：`in-memory` 无重启恢复；生产必须 `postgresql`。
- **恢复策略保守**：lease 过期一律进入 `RECOVERY_REQUIRED`，无自动重试/自动重放；需要人工裁决才能重跑。
- **Worker 单线程**：`JobWorker` 是单线程 + 有界队列（容量默认 100），无动态并发、无按 Agent 限流。
- **MCP 默认禁用**：`tools.mcp.enabled=false`，filesystem MCP 需显式启用（验收已通过）。
- **Artifact 未独立存储**：Artifact 内嵌在 ExecutionRecord，无独立 Artifact repository、下载 API 或对象存储。
- **无流式事件**：Executor 为同步 SPI，无 SSE/WebSocket 执行事件流。
- **Job 控制 API 不完整**：模型支持 `CANCELLED`/`RETRY_WAIT`/`RECOVERY_REQUIRED`，但 Controller 未暴露取消/暂停/重试接口（仅审批 resume）。
- **Hermes 计划为模板**：`HermesPlanner` 生成固定单 Step 或固定多 Agent 模板，尚未接入真实 LLM 规划。
- **OpenClaw 浏览器策略**：localhost 页面导航受全局安全策略限制（不可关闭策略绕过）。
- **前端包体**：production build 主 chunk 约 575.62 kB，留作治理项。

## 10.2 未来路线

- 多 Agent 串行计划真实验证（Phase 6-B：Browser → MCP → Coder → Tester 全链）。
- 自动恢复器：基于 `recovery_policy`/`failure_code` 的可配置重试与回退策略。
- Worker 并发扩展：多 worker/多实例消费、按 Agent 限流、取消/重试/幂等 API。
- Artifact 子系统：独立存储、下载、生命周期清理与访问控制。
- 流式执行事件：Executor 进度、日志流、SSE/WebSocket。
- MCP 生产启用：更多 MCP server（Git、Browser、Docker），统一权限与审计。
- 工程化：项目模板、自动初始化、CI/CD、团队共享与多 Agent 协作。
- 目标形态：让 AI 成为分析、编码、测试、运维四位一体的个人开发团队，始终保持可控、可追踪、可扩展、自动化。
